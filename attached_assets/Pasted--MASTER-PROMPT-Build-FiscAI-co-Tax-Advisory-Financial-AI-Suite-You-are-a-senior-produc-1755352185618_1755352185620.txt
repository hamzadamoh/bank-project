## 1) Tool #1 — **FiscAI Tax Counsel** (Premium Tax Advisory, RAG + Compliance)

**Goal:** Convert natural‑language tax questions into **grounded answers** with citations + optional exportable documents (memos, letters, checklists). Multi‑jurisdiction (start with Morocco + EU VAT + generic OECD concepts), multilingual (FR/EN/AR).

**Data sources (tenant‑scoped):**

* Official tax code/guides (public), administrative bulletins, circulars, treaty excerpts; firm’s internal notes/policies; prior memos (redacted).
* Index to vector DB with metadata: `jurisdiction`, `effective_date`, `article`, `topic`, `risk_level`, `doc_type`, `version`.

**Pipeline:**

1. Query understanding: normalize user question; extract entities (jurisdiction, period, taxpayer type, transaction type, thresholds); detect confidentiality.
2. Retrieval: hybrid search (BM25+dense) + jurisdiction/time filters + reranking; top‑k contexts limited by token budget; diversity enforced.
3. Answering model: strong reasoning model (server‑side) instructed **not** to reveal chain‑of‑thought; produce **structured answer**: (i) short answer, (ii) grounded explanation with numbered citations, (iii) compliance checklist, (iv) disclaimers/assumptions.
4. Verification: contradiction/consistency pass; hallucination guard (answer must reference citations).
5. Output: render markdown → PDF/Docx; offer *next actions* (forms, deadlines, alerts).

**System prompt (Tax Advisor):**

* Role: senior tax analyst. Provide **concise, jurisdiction‑aware answers** grounded in retrieved snippets.
* Rules: cite sources; never invent law; state assumptions; if ambiguous, ask the **minimal clarifying question**; forbid legal advice without context; no chain‑of‑thought exposure; provide **checklist** & **timeline** when relevant.

**UI/UX:**

* Chat with **jurisdiction switcher**; **scope selector** (CIT/VAT/withholding); **time window**; **confidence badge**.
* “View sources” side panel; export memo (PDF/Docx); save to knowledge base.
* Admin: upload corpus, versioning, deprecation dates, legal holds.

**Quality metrics:** groundedness (citation coverage), factual accuracy (expert review), latency, user satisfaction, memo export rate, zero‑answer/deflection rate.

## 2) Tool #2 — **Factoring Guardian** — Contrôle intelligent d’affacturage

**Goal:** Automate fraud/quality checks for factoring: extract from invoices/POs/contracts/BLs, cross‑match, detect anomalies, propose triage (validate/reject/alert), and track KPIs.

**Models & components:**

* **NuMarkdown‑8B‑Thinking** for **layout‑aware Doc → Markdown** conversion (weird layouts, complex tables).
* OCR fallback (tesseract/cloud/on‑prem) when images are poor; combine with NuMarkdown output for robustness.
* Post‑processing: Markdown → structured JSON according to schema below.
* Matching/Rules/ML: 2/3‑way match (Invoice↔PO↔Receipt), rules for critical anomalies, ML anomaly scoring (Isolation Forest/GBM), document forensics (PDF signatures, image tamper heuristics).

**Structured JSON schema (example):**

```json
{
  "invoice": {
    "supplier": {"name":"","tax_id":"","iban":"","address":""},
    "invoice_id":"","issue_date":"","due_date":"","currency":"",
    "totals": {"ht":0.0, "tva":0.0, "ttc":0.0},
    "lines": [{"sku":"","desc":"","qty":0,"uom":"","pu":0.0,"tva_rate":0.0,"line_total":0.0}]
  },
  "po_refs": ["PO-..."],
  "contract_refs": ["..."],
  "attachments_meta": [{"filename":"","hash":"","mime":"","pages":2}],
  "extraction_confidence": 0.0
}
```

**Matching & anomaly rules (non‑exhaustive):**

* **Duplicates**: same `{supplier_tax_id, invoice_id, date, amount}` already processed.
* **Amount mismatches**: totals vs sum(lines), tax breakdowns wrong, currency/FX mismatch.
* **Line‑item mismatches**: invoice lines not present/over‑delivered vs PO/receipt (tolerances configurable).
* **New/changed IBAN**: flag vs supplier master; require out‑of‑band verification.
* **Date anomalies**: issue date after due date; invoice before PO; weekend/public holiday anomalies (optional).
* **Document forensics**: invalid/absent signature; bitmap‑only with suspicious edits; mixed embedded/OCR text inconsistencies.

**Decision & evidence:**

* Output **decision**: `validate | reject | alert` with machine‑readable reasons (codes) and evidence (diffs, line refs, thumbnails).
* Log full trace for audit.

**UI/UX:**

* Upload area (drag‑drop); processing timeline; extracted fields preview; anomaly panel with fix suggestions; side‑by‑side invoice↔PO comparer; final decision.
* Dashboard: throughput, reject/alert rates, top anomaly codes, vendors at risk, cycle time.

**APIs:**

* `POST /affacturage/jobs` (files + metadata) → job\_id
* `GET /affacturage/jobs/{id}` → status + extraction JSON + anomalies + decision
* `GET /affacturage/dashboard` → KPIs (time‑bucketed)

**Quality metrics:** field F1 on key fields, line‑item match accuracy, false positive rate on critical alerts, mean cycle time.

**Compliance:** PII minimization; encrypted storage; per‑tenant keys; retention policies; audit trails.

## 3) Tool #3 — **Query Architect (NL ⇄ SQL)** — Expert Data Augmenté

**Goal:** Translate business questions **NL→SQL** *and* explain/validate existing queries **SQL→NL**: plain‑language summaries, schema mapping, optimization hints, guardrails, volumetry estimates, and teaching notes.

**Core model:** **Snowflake/Arctic‑Text2SQL‑R1‑7B** (on‑prem/VPC). Dialects: Snowflake (primary), plus Postgres, ANSI.

**Architecture (RAG + Arctic):**

* **Knowledge Base (KB)** (tenant‑scoped) indexing:

  * **Schema docs**: DDL (tables, columns, PK/FK), views, materializations, `connected_tables` graph.
  * **Business dictionary**: synonyms (ex. "encours" → `exposure_amount`), required filters (pays/BU), sensitive fields.
  * **Join rules**: allowed join paths/keys & cardinality expectations.
  * **Few‑shot pairs**: NL↔SQL examples validés; snippets optimisés.
  * Metadata: `name`, `summary`, `columns`, `keys`, `connected_tables`, `sample_queries`, `jurisdiction`, `sensitivity`.

**Orchestrator pipeline:**

1. **Normalization (NL or SQL)**

   * *NL input*: canoniser l’intent, extraire entités/mesures/filtres/période → “main clause”.
   * *SQL input*: parser **AST**, détecter tables/colonnes, agrégations, filtres, joins; vérifier dialecte.
2. **Retrieval multi‑paliers**

   * Exemples proches (pair NL↔SQL), docs de tables reliées, reranking (cross‑encoder).
3. **Generation**

   * *NL→SQL*: prompt **Arctic‑R1‑7B** avec dialecte, sous‑schéma, join rules, few‑shots, contraintes sécurité; sortie **SQL‑only**.
   * *SQL→NL*: LLM génère **explication structurée** (but, tables, clés, filtres, group‑by, métriques), **risques/perf** et **suggestions d’optimisation**.
4. **Validation & Guardrails**

   * Existence tables/champs, linter, blocage patterns risqués (cartésiens, `SELECT *` non justifié, scans larges non filtrés).
5. **Performance & volumétrie**

   * `EXPLAIN`/PROFILE → rowcount/cost; recommandations (pré‑filtres, partitions, LIMIT par défaut, index/hints si applicable).
6. **Sécurité**

   * RLS/ABAC injecte prédicats obligatoires (user/org/region); masquage PII; blocage tables interdites.
7. **Pedagogy**

   * Résumé mécanique (sans chaîne de pensée), lineage, chips de schéma et raisons de jointures.

**System prompt (Arctic Text2SQL, bi‑mode):**

* Mode = `<NL_TO_SQL | SQL_TO_NL>`; Dialect = `<DIALECT>`.
* Respecter schéma & join rules; préférer prédicats sélectifs; éviter `SELECT *`; ajouter `LIMIT 200` si absent (NL→SQL).
* En SQL→NL: produire **explication brève**, points de vigilance, et améliorations possibles.

**APIs:**

* `POST /text2sql/compile`  *(mode: nl\_to\_sql)* → `{ sql, warnings, plan_estimates, lineage }`
* `POST /text2sql/explain`  *(mode: sql\_to\_nl)* → `{ explanation, detected_entities, risks, plan_estimates, lineage }`
* `POST /text2sql/translate` *(mode: nl\_to\_sql | sql\_to\_nl)* → union des sorties ci‑dessus
* `POST /text2sql/validate` → `{ lint, policy_flags, safety }`

**UI/UX:**

* **Mode switch** NL→SQL / SQL→NL; zone de saisie avec suggestions (tables/colonnes/filtres).
* Panneaux: SQL généré **ou** Explication; **Explain/Volumetry**, Filtres sécurité, Teaching notes.
* Actions: **Refine** (ajouter filtre/aggregation), **Save snippet**, **Create chart** (phase 2).

**Quality metrics:** exec success, correctness vs réponses de référence, coût moyen, TTF‑result, taux de clarification, satisfaction.

## 8) Shared Prompting & Guardrails

**Do not reveal chain‑of‑thought.** Provide concise explanations (mechanical rationale, no step‑by‑step inner deliberation).
**Input sanitization:** block secrets, code injection, prompt leakage attempts.
**Output controls:** max tokens, safe‑completions, profanity/off‑topic filters.
**PII handling:** redaction on logs; structured outputs only.

**Fallbacks & resilience:**

* If retrieval is empty/low confidence → ask a minimal clarification or present relevant fields/examples.
* If model returns invalid SQL/JSON → auto‑repair with linter/grammar; otherwise show actionable error.
